| 2026-08-03 | **Input injection path survey** (M1 server work) | — | **This ROM is heavily hardened. Survey results:** ① InputManager reflection — hidden-API enforcement blocks `getConstructor` (NoSuchMethodException even via getDeclaredConstructor). ② `InputManager.getInstance()` — NPE at InputManager.java:354 (`requireNonNull`) even with main looper prepared; MIUI build needs something app_process lacks. ③ **uhid** — `CREATE2` write returns EINVAL for EVERY size/descriptor combination incl. the kernel's own sample descriptor → Xiaomi kernel patch disables it. ④ **uinput `UI_SET_PROPBIT`** — EINVAL for both INPUT_PROP_DIRECT and INPUT_PROP_POINTER → virtual devices cannot claim to be direct-touch. ⑤ `/dev/input/event*` write — EACCES (SELinux `denied { write } ... input_device chr_file` from `u:r:shell:s0`). ⑥ **uinput classic API WORKS** (see next row). |
| 2026-08-03 | **uinput classic API injection** (M1 server) | **PASS (kernel level)** | `/dev/uinput` is `crw-rw---- uhid:uhid` and **shell uid is in the uhid group** → open+ioctl OK. Sequence: `UI_SET_EVBIT/KEYBIT/ABSBIT` + `write(uinput_user_dev)` + `UI_DEV_CREATE` → device appears as "laphone-touch", Android InputReader registers it (`Classes: TOUCH | TOUCH_MT`, `Enabled: true`). Kernel events verified via `getevent -c N /dev/input/eventN` (exact coords, BTN_TOUCH down/up + SYN per tap). **Gotchas:** ① fd lifetime — dropping the Rust `File` closes the fd; a stale-fd `UI_DEV_CREATE` returns EBADF (looks like a kernel rejection, is a code bug). ② **ABS ranges must match the display aspect** — a square 0..4095 range maps X to 0..2399.4 (display-scaled) instead of 0..1079.9 → taps land off-screen. Copy the real fts touchscreen: **10 units per pixel, X 0..10799, Y 0..23999**. ③ Without `INPUT_PROP_DIRECT` (blocked, see above) InputReader classifies the device as `Sources: MOUSE`, `DeviceType: POINTER` (touch→mouse-pointer). ④ POINTER mode consumes legacy `ABS_X/ABS_Y` — the event stream must update those, not just `ABS_MT_*`. |

| 2026-08-03 | MIUI keyguard dismissal via adb | FAIL | `wm dismiss-keyguard`, `input keyevent 82`, `input swipe` (full-length, bottom-edge start), `locksettings set-disabled true` + SystemUI restart — **none dismiss the keyguard** (`isKeyguardShowing=true` persists). | 2026-08-03 | **POINTER-mode tap verification** (unlocked state) | **FAIL** | With the user's phone unlocked: uinput tap on a settings entry (WLAN, coords verified via uiautomator dump) → **no effect**; `input tap` on the same coordinates → **works**. Retried with a hover (position-only report + 30ms) before the click → still no effect. System navigation gestures (swipe-up home) also don't trigger from POINTER-mode touches. **Conclusion: on this ROM the uinput path is a dead end for touch** — kernel blocks INPUT_PROP_DIRECT (→ POINTER classification) and POINTER-mode taps never become clicks. The M1 low-latency input server is **disabled by default** (`LAPHONE_INPUT_SERVER=1` to opt in; kept for devices where POINTER-mode works). M0's `input`-command pipe remains the input path. |
